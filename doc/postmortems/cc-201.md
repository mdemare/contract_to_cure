# cc-201: Split frontend player actions

## What went right

The large player action module separated cleanly along workflow boundaries. Map clicks, pawn movement, and movement-card follow-ups now live in `movement_actions.js`; routine turn actions live in `ordinary_player_actions.js`; and event-card request execution lives in `action_card_requests.js`. The original `player_actions.js` remains a small compatibility facade, while application consumers import their owning modules directly.

Separating action mode, action-card source, and hand-limit coordination into dependency-neutral modules made it possible to remove the frontend's static import cycles instead of shifting them elsewhere. Explicit DOM events handle movement follow-ups and game-state UI refresh, while a callback registry handles card-selection prompts that may register after state loading. A static dependency audit found no remaining cycles. The focused import smoke test passed alongside all JavaScript tests, and the full Ruby suite passed with 127 tests and 743 assertions.

## What went wrong

The dependency cycle was wider than the four modules named in the ticket. `game_state.js` reached the UI layer, the UI reached action buttons, and action buttons reached player actions; the request helper also dynamically imported player actions and card selection. Resolving the underlying ownership problem therefore required changes to state-to-UI coordination and one redundant UI import in addition to extracting functions.

The first Ruby suite run failed because an existing source-level research-station test still inspected `player_actions.js`. Updating that assertion to inspect the new ordinary-action owner fixed the failure, and the complete suite passed on rerun. The repository's lightweight JavaScript tests can prove imports and isolated DOM contracts, but they do not yet exercise the multi-step browser workflows affected by the new event boundaries. A separate pre-existing restart-menu path also calls a nonexistent UI export.

## Final thoughts

State modules should expose state and notifications without importing downstream UI or workflow modules. That one-way rule, combined with direct imports from cohesive action owners, gives the frontend a dependency structure that is easier to inspect and change. Compatibility facades are useful at migration boundaries, but new consumers should continue importing the actual owner.

The import smoke test is an appropriate fast guard for the extracted public boundaries. Ticket `cc-220` tracks realistic integration coverage for movement, action cards, mode resets, state refresh, hand-limit registration, and repeated initialization. Ticket `cc-218` recorded the unrelated restart-menu UI call discovered during the audit.

# cc-223: Contain modal keyboard focus

## What went right

A dependency-free modal lifecycle now serves general card selection, mandatory hand-limit discard, Resilient Population, Share Knowledge, and Forecast. It cycles keyboard focus through currently available controls, makes background elements inert, and restores their previous state when the final dialog closes. Shared cleanup also handles an underlying dialog finishing while a mandatory prompt remains above it.

The implementation preserves optional Escape cancellation, initial focus, and focus restoration, including the asynchronous event-card-to-Forecast transition. Mandatory discard and Forecast remain open after failed requests with accessible retry paths. Forecast ordering controls retain focus when moving a card to a boundary disables the button that invoked the move.

Verification passed with 128 Ruby tests and 744 assertions, all 15 standalone JavaScript tests, and temporary Chromium checks covering the five workflows, dynamic controls, background isolation, retries, empty selectors, nested cleanup, and focus restoration. No tests were added to the repository, as requested. The accepted implementation was committed as 038f43d.

## What went wrong

The original dialogs duplicated focus setup and cleanup, while event-card code could remove a backdrop directly. Initial focus and aria-modal declarations did not prevent keyboard users from reaching background controls. Discard and Forecast also dismissed their dialogs before their requests succeeded, leaving failures without an immediate completion path.

The first browser pass caught a regression introduced during the refactor: the Resilient Population cancel listener referenced the new close callback before initialization. Wrapping that call in a deferred handler fixed it before the final verification. Browser setup also needed the installed ARM Chromium executable and loaded city data for Share Knowledge; correcting those harness assumptions separated fixture errors from application failures.

The existing suites did not detect the focus initialization regression. Temporary browser checks provided useful evidence but do not protect future changes. The follow-up audit found no existing modal-focus regression ticket. An older postmortem referenced cc-220 for broader integration coverage, but that key was not resolvable in noca and was not treated as available coverage.

## Final thoughts

Focus containment must cover the entire dialog lifecycle: changing controls, asynchronous requests, transitions, nested prompts, and restoration. A shared owner makes those responsibilities easier to maintain than independent handlers in every workflow.

Test ticket cc-231 specifies durable browser coverage for these behaviors, including request failures and mandatory completion paths. FrontendUI (cc-118), TechnicalDesign (cc-35), and FunctionalDesign (cc-34) now describe the implemented behavior while preserving newer map documentation; each description remains below 500 words. No unresolved additional bug was identified, so no duplicate bug ticket was created. This postmortem is intentionally left uncommitted for dispatcher publication.

# CC-218: Fix restart UI refresh

## What went right

The failure was isolated to the menu restart success path. `loadGameState()` already fetched the new authoritative state and called `updateGameUI(gameState)`, so removing the subsequent unsupported `updateUI()` call restored the intended behavior without changing the API or game rules.

Extracting the restart request into an exported function made the workflow directly testable. The focused test verifies that a successful menu restart posts to `/restart_game`, reloads state exactly once, and dismisses the game-over dialog. The complete suite passed with 128 runs and 744 assertions.

## What went wrong

The original implementation dynamically imported a symbol that `ui.js` did not export. Because the invalid call ran after `loadGameState()` had already refreshed the interface, the restart appeared partly successful before falling into the generic error handler. Existing backend restart tests confirmed state reset behavior but did not execute this frontend orchestration path, allowing the mismatch to remain unnoticed.

During verification, an initial command assumed a nonexistent `bin/ruby` wrapper. Rerunning with the repository's configured Ruby command succeeded and did not reveal a project issue.

## Final thoughts

Frontend workflows should have one clear state-to-UI refresh boundary. In this case, `loadGameState()` owns that responsibility, and callers should not attempt a second render through another module. Small behavioral tests around asynchronous menu actions are valuable because they catch module-export mismatches and ordering errors that endpoint tests cannot cover.
